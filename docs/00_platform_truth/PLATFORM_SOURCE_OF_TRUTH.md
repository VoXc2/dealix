## 2. هندسة العرض الكنسية / Canonical offer architecture

1. **Execution Diagnostic** — تحديد workflow واحد ذي أثر اقتصادي، baseline، التسرب/الاختناق، الأنظمة، حدود البيانات، صاحب القرار ومعايير الإثبات. لا سعر عام ولا Checkout ولا التزام شراء.
2. **Qualified Discovery + Customer-Specific Quote** — تثبيت المشكلة والنطاق والبيانات وشروط البدء ومعايير القبول، ثم عرض خاص بالعميل فقط.
3. **Outcome Sprint** — تنفيذ محكوم ومخصص للعميل يركز على نتيجة قابلة للقياس. قد يكون تقريبًا 4–6 أسابيع عندما يناسب الحالة، لكنه ليس وعد مدة ثابتة أو منتجًا ذا سعر عام.
4. **Proof Review** — مقارنة النتيجة بالـbaseline وفصل activity عن verified value.
5. **Dealix Runtime** — تشغيل مستمر مُدار/منصّي للـworkflows التي أثبتت قيمتها، مع monitoring + governed execution + proof + executive command.

### Compatibility authority

حتى يكتمل migration منفصل ومقبول للسلطة التشغيلية، يمكن أن تبقى معرفات داخلية تاريخية مثل:

- `free_mini_diagnostic`
- `revenue_command_pilot_30d`

كـ **operational compatibility IDs فقط**. لا تعيد هذه المعرفات الأسماء القديمة إلى الواجهة السوقية، ولا تمنح fixed price أو checkout أو مدة عامة أو نتيجة مضمونة.

### Pricing / commercial authority

- الأسعار **customer-specific quote only** بعد Discovery.
- لا public fixed-price table.
- لا public checkout authority.
- لا guaranteed revenue / ROI / result claim.
- `Outcome Sprint` = customer-specific implementation fee.
- `Dealix Runtime` = managed/platform base + bounded execution/usage allowance + excess usage عندما يكون ذلك مناسبًا ومقبولًا تعاقديًا.
- أي outcome-linked bonus يتطلب attribution موثقًا وقابلًا للمراجعة.
- الأسعار أو أسماء العروض التاريخية في الريبو هي `SUPERSEDED_UNLESS_REVALIDATED` وليست authority.

| Command OS | Executive priorities, decisions, approvals, risks and next actions. |

`Official/first-party signal -> WHY THEM -> WHY NOW -> account dossier -> buying group -> pain hypothesis -> proof potential -> eligible relationship/channel -> contextual founder-quality interaction -> reply intelligence -> discovery -> quote -> cash -> delivery -> proof -> expansion`

2. events and real interactions;
3. founder/company authority + AEO/search inbound;

## 9. Truth firewall / Non-negotiables

Keep these distinctions strict:

- research != relationship
- public contact != consent
- lead != buyer intent
- draft != sent
- quote != invoice
- invoice != payment
- payment marker != verified cash
- synthetic/demo != customer proof
- PR != production
- historical PASS != current exact-head PASS

And everywhere:

- no scraping as a growth shortcut;
- no cold WhatsApp automation;
- no mass/unapproved LinkedIn account automation;
- no external auto-send without the required current authority;
- no fake proof, fake relationships or guaranteed ROI/revenue claims;
- no PII in public case studies without appropriate authority;
- no external action on a customer's behalf without explicit applicable approval;
- no public fixed price/checkout authority unless a later accepted doctrine explicitly changes this.
